# 日高オーダー Supabase・端末内併用の保存方式

- 設計版: 1
- 作成日: 2026-09-01
- 対象アプリ: 日高オーダー v1.9.0
- 状態: 保存方式の設計のみ。接続実装は未実施

## 1. 採用する方式

現在の端末内保存を残し、Supabaseを共有・長期保存先として追加する。

```text
画面操作
  ↓ まず端末内へ保存
localStorage + 同期待ちキュー
  ↓ 通信可能・ログイン済みなら送信
Supabase
  ↓ 別端末や更新分を取得
端末内データへ反映
```

画面は常に端末内データを先に更新する。通信待ちで操作を止めないため、電波が弱い店内でも現在と同じように使える。

## 2. 保存先の役割

| 保存先 | 役割 |
|---|---|
| `localStorage` | 画面表示、オフライン利用、未記録注文、同期待ちデータ |
| Supabase | 端末間共有、長期保存、ハラケンAI・焼酎キープ管理との将来連携 |
| GitHubのCSV | 新規利用時の初期メニュー、復元用の基準データ |
| 完全バックアップJSON | 利用者が保管できる手動バックアップ |
| Service Worker Cache | HTML・JavaScript・CSVなどアプリ本体のオフライン起動 |

GitHubのCSVを日々の保存先にはしない。スマホで編集したメニューや履歴は、ログイン後にSupabaseへ保存する。

## 3. 保存の流れ

### 3.1 オンライン・ログイン済み

1. 操作結果を端末内へ保存する。
2. 同期待ちキューへ操作を1件追加する。
3. Supabaseへ `upsert` または論理削除を送る。
4. 成功した操作を同期済みにする。
5. 最新のサーバー更新を取得して端末内へ統合する。

### 3.2 オフライン

1. 操作結果を端末内へ保存する。
2. 同期待ちキューへ追加する。
3. 画面に「端末に保存済み・同期待ち」と表示する。
4. 通信が戻ったとき、作成順に自動送信する。

### 3.3 未ログイン

現在と同じ端末内保存だけで利用できる。Supabase同期を有効にするときだけログインを案内する。初回からログインを必須にして、現在の操作性を悪化させない。

## 4. 端末内に追加する同期情報

現在の `hidaka-order-v1` データを維持し、次の管理情報を追加する。

| 項目 | 内容 |
|---|---|
| `sync.deviceId` | 端末を識別するランダムID |
| `sync.lastPulledAt` | 最後にSupabaseから取得した時刻 |
| `sync.pendingOperations` | 未送信操作の一覧 |
| `sync.lastError` | 最後の同期エラー。利用者向け表示用 |
| `sync.enabled` | Supabase同期を使うか |

同期待ち操作には、`operationId`、対象テーブル、対象ID、操作種別、更新データ、作成時刻、試行回数を持たせる。同じ操作を再送しても、安定IDと `upsert` により重複を作らない。

## 5. データ別の同期方法

| データ | 送信方法 | 競合時の扱い |
|---|---|---|
| 店舗 | `upsert` | 新しい `updated_at` を採用 |
| メニュー | `upsert`／論理削除 | 新しい `updated_at` を採用。削除済みを復活させない |
| 店舗設定 | `upsert` | 新しい `updated_at` を採用 |
| 当日の品切れ | 日付・メニューIDで `upsert` | 同じ日は品切れを優先。翌日は対象外 |
| 来店 | 安定した来店IDで `upsert` | 新しい `updated_at` を採用 |
| 注文明細 | 安定した明細IDで `upsert` | 来店単位で整合性を確認 |
| AI提案 | 新しい提案として追加 | 同一IDだけ再送を無視 |
| フィードバック | 来店IDで `upsert` | 新しい `updated_at` を採用 |

## 6. 注文記録の保存単位

「この注文を記録」では、次をひとまとまりとして扱う。

1. `visits`
2. `recommendation_runs`
3. `recommendation_items`
4. `order_items`
5. 入力済みなら `visit_feedback`

端末内には先に全部保存する。Supabase側では、将来の保存関数またはトランザクションを使い、途中までしか保存されない状態を防ぐ。

組み直す途中の案は端末内に置き、初期実装では「注文を記録した時点の最終提案」だけをSupabaseへ保存する。これにより不要な提案履歴の増加を防ぐ。

## 7. メニュー編集の保存

- 商品追加時に端末側で安定IDを作る。
- 価格・区分・タグ・季節・提供状態を編集したら、同じIDで更新する。
- 削除はSupabase上で `deleted_at` を設定する。
- 別端末は `deleted_at` がある商品を候補に表示しない。
- 過去の `order_items` は削除せず、注文時の商品名と価格を残す。

## 8. 初回同期

初回同期は安全のため自動実行せず、利用者が選んだ完全バックアップを使う。

1. スマホ公開版から最新の完全バックアップを保存する。
2. 新しい同期対応版でバックアップを読み込む。
3. 件数と合計を画面で確認する。
4. 「Supabaseへ初回保存」を1回だけ実行する。
5. Supabase側の件数と端末内件数を照合する。
6. 一致後も元JSONを削除しない。

既にSupabaseにデータがある場合は、勝手に全置換せず「追加・更新される件数」を事前表示する。

## 9. 別端末での開始

1. 同じアカウントでログインする。
2. Supabaseから店舗・メニュー・履歴・設定を取得する。
3. 端末内が空ならそのまま保存する。
4. 端末内に既存データがある場合は、自動上書きせず初回統合の確認を出す。

## 10. 同期状態の画面表示

基本画面を複雑にせず、データ管理画面に次の状態だけ表示する。

- `同期済み`
- `端末に保存済み・同期待ち 3件`
- `ログインが必要です`
- `同期に失敗しました・再試行`

通常操作のたびに通知を出さず、問題がある場合だけ目立たせる。

## 11. 認証と安全性

- 初期案はメールのマジックリンクまたはワンタイムコードでログインする。
- 全テーブルでRLSを有効にし、`owner_id = auth.uid()` の行だけ読み書きできるようにする。
- ブラウザにはSupabaseの公開可能なキーだけを設定する。
- `service_role` キー、パスワード、管理用秘密情報はGitHubやブラウザへ置かない。
- 将来のハラケンAIや焼酎キープ管理も同じSupabase Authの利用者IDで関連付ける。

## 12. エラー時の方針

- Supabase送信失敗でも端末内保存を取り消さない。
- 同期キューを消さず、次回起動・オンライン復帰・手動再試行で再送する。
- ログアウトしても端末内データを自動削除しない。
- サーバーと端末のどちらを採用したか、同期ログで追跡できるようにする。
- 破損データは無理に送信せず、対象と理由を表示する。

## 13. 採用決定

この段階では次を採用する。

1. 端末内を操作中の保存先として維持する。
2. Supabaseを共有・長期保存先にする。
3. オフライン操作は同期待ちキューに残す。
4. 注文記録時の最終提案だけをSupabaseへ保存する。
5. 当日の品切れはSupabaseへ同期し、日付が変われば候補から自動的に外す。
6. メニューと設定の競合は、基本的に新しい更新時刻を採用する。
7. 初回移行はバックアップを確認してから手動実行する。
